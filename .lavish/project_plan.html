Local-First Password & Clipboard Sync

Project Implementation Roadmap & Technical Design

No Cloud E2E Encrypted BLE & Wi-Fi Direct

Current State

We have successfully initialized the .NET C# shared solution and built the Win32 Clipboard Listener background daemon. The daemon reliably captures clipboard changes on Windows.

Desired Behavior

The Android and Windows apps must automatically find each other locally (BLE), seamlessly exchange encrypted clipboard data, and merge Vault changes deterministically without conflict (CRDTs).

Implementation Phases

  • Foundation
  • Connectivity
  • CRDT Vault
  • Native UI

Phase 1: Foundation (Current) Active

  • Win32 Clipboard Listener Daemon
  • Implement AES-256-GCM and Argon2id inside CoreLib
  • Set up Android MAUI Accessibility Service for clipboard monitoring

Phase 2: Discovery & Transport

  • Generate & Scan QR codes for initial zero-trust key exchange
  • BLE Discovery: Broadcast only on phone unlock/clipboard change to save battery
  • Wi-Fi Direct: Automatic upgrade protocol for large payloads (Images)
  • ChaCha20-Poly1305: Encrypt all payloads in transit

Phase 3: Vault CRDT Synchronization

  • Define local SQLite database schema
  • Implement Vector Clocks and Conflict-Free Replicated Data Types (CRDTs) to handle offline edits

Phase 4: Native User Interfaces

  • Windows: WPF or WinUI 3 shell around the Daemon
  • Android: .NET MAUI frontend with biometric unlock

Risks & Decisions Needed

Android 10+ Clipboard Restrictions

Background clipboard reading is blocked on Android 10+. Our Accessibility Service must be robust enough to parse clipboard changes or UI focus events reliably without being killed by the OS.

Decision: What to build next?

Do we want to build the `CoreLib` crypto engine (AES/Argon2id) first, or immediately start scaffolding the Android MAUI application to prove the cross-platform viability?

Frequently Asked Questions

Will the encryption make syncing slower?

Short answer: No.

We are using hardware-accelerated encryption algorithms (AES-GCM for the local vault and ChaCha20-Poly1305 for transport). These operate at several gigabytes per second on modern CPUs and ARM chips (phones). For small payloads like passwords, encryption takes less than a millisecond. For large clipboard photos (e.g., 5MB), it will encrypt in a fraction of a second, which is much faster than the time it takes to transmit over BLE/Wi-Fi Direct.
